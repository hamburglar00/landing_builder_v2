# Template 7: integración y demo

La landing normal usa `/l/{slug}` y `/api/template7/start`. Sin API2, start responde `integration_pending`. Nunca usa las credenciales demo por un error de API2.

La demo usa `/l/{slug}/testing` (también `/{slug}/testing` si el host apunta a esta aplicación). La pantalla de acceso envía la clave por POST, con rate limiting durable mediante `consume_template7_rate_limit`. Una clave válida crea una cookie `t7_demo` HttpOnly, firmada con HMAC-SHA256, válida cuatro horas y ligada a landing ID y slug. La página reutiliza el renderer de Template 7 pero no ejecuta Pixel, CAPI, Contact, journey-start ni atrio-click. El clic envía el contexto `X-Template7-Demo-Context: testing`; **ese header no autoriza nada**: start exige también la cookie firmada, configuración activa, landing y asesor permitidos, proveedor Rey de Ases y todas las validaciones normales de asignación/plan. El `lb_cid` real sigue protegiendo el rate limit; internal-chat y el gateway reciben el `TEMPLATE7_DEMO_DEVICE_ID` fijo, por lo que los visitantes demo comparten identidad y chat.

Para habilitar la demo, configurar exclusivamente en el servidor `TEMPLATE7_DEMO_ENABLED=true`, `TEMPLATE7_DEMO_ACCESS_KEY` y `TEMPLATE7_DEMO_SESSION_SECRET` de al menos 32 bytes, allowlists UUID `TEMPLATE7_DEMO_LANDING_IDS` y `TEMPLATE7_DEMO_ADVISOR_IDS`, `TEMPLATE7_DEMO_DEVICE_ID` UUID, y `TEMPLATE7_DEMO_REY_USERNAME`/`TEMPLATE7_DEMO_REY_PASSWORD` de una cuenta de prueba. Desactivar con `TEMPLATE7_DEMO_ENABLED=false` o retirando cualquiera de los requisitos. No usar `NEXT_PUBLIC_` ni `test_event_code` para estas variables.

El contrato servidor-servidor con internal-chat usa `INTERNAL_CHAT_ORIGIN` e `INTERNAL_CHAT_PLAYER_RESOLVE_KEY`, **no** `INTERNAL_CHAT_GATEWAY_SECRET`. `POST /api/gateway/players/resolve` recibe `advisor_id`, `advisor_slug`, `device_id`, `name`, `landing_id`, `landing_slug`, `atrio_client_id`, `promo_code`, `target_provider` y `source: "landing_builder"`. El servidor obtiene `target_provider` exclusivamente de la configuración persistida y validada de la landing, incluso en la demo Rey de Ases; no acepta la elección del navegador. La respuesta debe incluir y validar `advisor_id`, `advisor_slug`, `player_id`, `device_id`, `created`, `player_provider_account_id`, `target_provider` y `provider_account_created`. `player_id` identifica al jugador por `advisor_id + device_id`; `player_provider_account_id` identifica su relación con un proveedor. El `platform` del dispositivo es un concepto diferente de `target_provider` y no determina esa relación.

`player_provider_account_id` permanece interno en `ResolvedPlayer`: todavía no se envía a `/api/handoffs` porque el gateway no confirmó ese contrato. El siguiente paso es transportarlo por el gateway hasta el contexto firmado del widget. La cuenta demo sustituye solo API2 y sus credenciales viajan únicamente al gateway por `/api/handoffs`, nunca al navegador.

El rate limit requiere aplicar la migración `supabase/migrations/20261008203009_template7_rate_limits.sql` antes de desplegar la aplicación: crea la tabla privada y la RPC `consume_template7_rate_limit`. Configurar `TEMPLATE7_RATE_LIMIT_HMAC_KEY` solo en el servidor; nunca en variables `NEXT_PUBLIC_`. El dominio `landing.panelbotadmin.com` figura en el proyecto como destino del motor clásico, mientras que el constructor publica por defecto en `mkt.panelbotadmin.com/l/{slug}`. La ruta corta funcionará en el dominio clásico solo si ese host se dirige a esta aplicación; aquí no se cambia DNS.
